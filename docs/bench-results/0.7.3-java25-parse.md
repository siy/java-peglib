# 0.7.3 — Java25 parse benchmark and hot-path identity proof

Measured 2026-08-22 on `release-0.7.3`.

## Why there is a proof here and not just a benchmark

CLAUDE.md requires a JMH re-run after any change touching `LexerEngine.lex`, `CstArrayBuilder`,
`TokenArray.spliceLex`, or generated parser emit. 0.7.3 touched two of those: `LexerEngine.lex`
(nesting interception) and `LexerGenerator` (the emitted lex loop).

A benchmark alone could not have answered the question, for a reason worth recording: **the stored
baselines in this directory are from the 0.4.x era and use a different parameter axis** —
`(variant)` rather than `(fixture)` — so they are not comparable to the current
`Java25ParseBenchmark`. Running the benchmark on this branch produces absolute numbers with
nothing to compare them against, which is not a regression check.

So the hot path was verified by identity instead, which is stronger than a timing comparison
because it is exact and not subject to run-to-run noise.

## Identity proof

`GLexer` and `GParser` were generated for `java25.peg` from `main` (`d548f2a`) and from
`release-0.7.3`, and compared:

| artifact | result |
|---|---|
| `GParser.java` | **byte-identical** |
| `GLexer.java` | 84 differing lines, **all of them `RESOLVERS` `.put(...)` lines** (zero non-`.put` differences); the two files are identical as multisets of lines |

The `.put()` calls populate a `java.util.HashMap`, whose lookup behaviour does not depend on
insertion order. Same calls, same resulting map, different emission order — so the generated
lexer and parser for `java25.peg` are **semantically identical** across the two revisions and the
parse hot path is unchanged by construction.

The reordering is not incidental: it *is* the 0.7.3 reproducibility fix. On `main` the order is
randomised per JVM run (`Map.copyOf`); on `release-0.7.3` it is deterministic. That is why the
diff exists at all, and why it is confined to those lines.

This also explains why no timing regression was expected: `java25.peg` declares no `%nest`, so the
nesting interception is not emitted into its lexer at all, and the remaining 0.7.3 changes
(`RuleClassifier` classification, `DfaBuilder` map copying) run once per grammar at
`fromGrammar` time, never per token.

## Reproducing the identity proof

Generate from both revisions and compare. The comparison must normalise for `.put` ordering only
if the older side predates the reproducibility fix:

```bash
git worktree add /tmp/wt-main <baseline-ref>
# build both, then generate GLexer/GParser for java25.peg from each
diff old.parser.java new.parser.java                      # expect: identical
diff old.lexer.java new.lexer.java | grep -cv '\.put('    # expect: 0 non-.put differences
sort old.lexer.java > a; sort new.lexer.java > b; diff -q a b   # expect: identical
```

Against any two revisions from 0.7.3 onward both sides are deterministic, so plain `diff` should
report no differences at all — that is the point of the fix.
